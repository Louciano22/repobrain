# Ranking benchmark foundation

`pnpm test` runs the existing synthetic provider-repository regression suite and prints one machine-readable `CREAMSODA_BENCHMARK_JSON=` line. The v1 report contains per-query paths and Hit@5, Precision@5, Recall@5, and reciprocal rank, plus their aggregate means. It scores unique file paths rather than individual chunks. A missing result counts against Precision@5.

The corpus is generated in `packages/testing/src/ranking-eval.test.ts`. Its seven queries and declared relevant paths are public, synthetic development fixtures—not proprietary evaluation data, a held-out test set, or evidence of real-world performance. Existing top-k and source-over-artifact assertions, a Hit@5 gate of 1.0, a synthetic MRR@5 floor of 0.85, and repeated-ranking determinism are CI gates. These are regression checks for this toy fixture, not product-quality claims. Reports contain no source excerpts or provider credentials.

Next steps: collect larger, separately reviewed repositories and judgments from more varied codebases, then set defensible quality thresholds after recording repeated baselines. Keep any private customer corpus outside the public repository, subject to consent and retention rules.

## Public evaluation split

`packages/testing/src/heldout-fixtures.ts` contains two small synthetic repository shapes (checkout web app and background worker). Twelve separately declared query judgments in `heldout-judgments.ts` are disjoint from the seven development queries. These public fixtures are held out **from development tuning** only; they are visible in the repo, neither secret/proprietary nor representative of real customer code. Do not tune retrieval against this split or treat it as an unbiased generalization estimate after tuning.

`pnpm test` runs Cream Soda retrieval in deterministic `exact` mode and a dependency-free binary token-overlap baseline over the **same indexed files, queries, labels, and K=5**. `CREAMSODA_PUBLIC_EVAL_JSON=` reports reviewed SHA-256 of fixture contents and judgments, SHA-256 of the compiled retrieval module, indexed file counts, aggregate metrics, and small per-repository and per-intent slices. Both systems use unique file paths, and missing results count against Precision@5. The report deliberately omits per-query text, labels, source excerpts, and credentials so that the output format can be reused with a future access-controlled corpus. The test ensures fixture integrity and result accounting but imposes no quality threshold on this new split; record and review the baseline before setting one. The score of these twelve simple synthetic questions is not a product-quality estimate. The test writes only its own small, known fixtures to an owned temporary directory; it is **not** a safe runner for arbitrary or customer repositories. A public repo cannot host private judgments. Never print or commit private customer fixtures to CI, and review consent, retention, file limits, and sensitive path handling before any private-corpus run.

The v2 public evaluation collapses indexed chunks into distinct file paths **before** taking five results, matching the local opt-in runner's scoring unit. v1 took five chunks first, so its Hit@5 and related scores are not directly comparable to v2. The CLI and search page request `searchCodebase` with `resultUnit: "file"`, displaying each file once with its highest scoring excerpt; the default API, MCP tool, and context packs still return chunks. Evaluation uses exact scoring over indexed chunks; the CLI and UI normally use hybrid mode, which can change order if a local semantic provider is active. The fixture and judgments remain unchanged; the split is still public and must not be used for tuning.

## Opt-in local evaluation of private judgments

The separate `packages/testing/dist/private-eval-cli.js` runner reads a bounded JSON judgment file **outside this checkout and outside its repository root** and existing indexes below a dedicated, operator-approved `--repos-root`. It does not index source, run repository code, execute builds, make network requests, or write to the index. It ranks all indexed chunks in exact mode, collapses by unique file path before K=5, and compares against binary token overlap on the same indexed content. It prints one aggregate-only JSON object: case count, repository count, files represented by indexed chunks, and total Hit@5, Precision@5, Recall@5, MRR@5 for both rankers. It never prints case IDs, repo names, file paths, query/label text, or source excerpts. Missing results count against Precision@5. No quality gate is set.

Run only against trusted, stable, previously indexed repositories whose content you have permission to evaluate. The current indexer and store are **not a hostile-input sandbox** and are not safe against concurrent filesystem mutation. A local index can already contain source text and sensitive data; inspect and protect it separately. Keep the evaluation root and corpus outside Git and CI, with restricted permissions. Create the root marker to make deliberate authorization explicit:

```sh
mkdir -p /path/to/private-evaluation/repos
printf 'cream-soda-private-eval.v1\n' > /path/to/private-evaluation/repos/.cream-soda-private-eval-root
# Put trusted pre-indexed repos immediately below this root, e.g. repos/project-one/.repobrain/store.json.
node packages/testing/dist/private-eval-cli.js --repos-root /path/to/private-evaluation/repos --corpus /path/to/private-evaluation/judgments.json --allow-private-eval
```

The corpus format is `{ "schemaVersion": "cream-soda-private-judgments.v1", "cases": [{ "repo": "project-one", "query": "Where is a task acknowledged?", "relevantPaths": ["src/queue/consumer.ts"] }] }`. `repo` is a single directory name directly under the approved root. The runner rejects duplicate normalized repository/query pairs, absent judged files, unsafe paths, symlinks, oversized input, and missing opt-in. The judgment file is capped at 1 MiB and 100 cases; each store at 32 MiB and 20,000 chunks; combined stores at 64 MiB, 40,000 chunks and 32 MiB of chunk text. CLI errors are generic, but **shell history, process arguments, wrappers, and terminal logs may expose the explicit corpus/root paths**. Use a trusted machine, offline environment, and no ambient provider secrets. The runner's bounded descriptor reads do not eliminate filesystem replacement races.

Before a real run, keep a restricted private provenance ledger alongside the corpus: ownership and consent/license, retention/deletion date, collection dates, evaluation split assigned before tuning, judgment instructions and adjudication, corpus version, source index versions, code revision and lockfile hash, Node version, and reviewer. Neither private corpus nor ledger belongs in this public repo. Treat the aggregate metrics as descriptive only, especially with small data; the public synthetic split and this opt-in local runner provide no independent proof of product quality.

Aggregate counts and scores can themselves disclose membership or performance on a small private corpus. Keep the printed report in restricted local storage; do not publish it, attach it to CI, or upload it as a build artifact without a separate disclosure review.
